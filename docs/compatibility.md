## Scoped .NET caller adaptation, 2026-10-11

The fixed generator derives a direct method's optional scope only from its single lookup parameter and a matching `TypertContextMap` entry with the same wire type ([analyzer](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/typert/generator/src/analyzer.ts#L1177)). Receiver Context invocation is separate: its identity chooses the Host Context before Service admission and lookup resolution. The [Client Gateway](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/api/gateway/src/client/index.ts#L390) obtains scoped identities through the current Client adapter.

The .NET author uses assembly-level `TypertContext(key, typeof(Wire))` declarations instead of TypeScript declaration merging. Extraction retains those declarations from the compilation and its assembly references in the one current model; Host binding and caller emission read the same facts. Receiver Context generation uses the declared wire type, replacing its earlier hard-coded string. The adapter still owns actual identity and Context resolution; the attribute adds no runtime registration. Old artifacts lacking these declaration facts must be re-extracted, without a parallel reader or format generation.

The generated `ForContext(callerContext, registry)` view supplies the C# equivalent of contextual Service access. It explicitly selects the scoped signature; the parent client supplies direct signatures, rather than reproducing JavaScript's dynamic fallback between argument lists. Receiver-scoped methods do not expose a public raw-identity method. Direct lookup-scoped methods retain their ordinary identity argument and gain a view method without that argument. Lookups without a matching Context declaration, or with multiple lookup parameters, remain direct. A scoped call enters the existing Cordis execution domain to read the current adapter and identity each time. It does not cache either, manufacture Contexts or own the caller's Context/registry/HttpClient. Parent-client disposal and existing stream cancellation retain their current owners.

The upstream absence sentinel maps to `Undefined.Value`. For reference identities, explicit null stays present in the internal request envelope and is validated by the Host codec, rather than becoming absence or an STJ serialization failure. Value identities must have the declared CLR type before a typed invocation can be made. Host lookup object types stay in declaration analysis; standalone callers project only their wire identity types. This extension does not implement owned Context values, Peer/uplink, complete event semantics or the equivalent browser scoped facade. [Authoring](authoring.md) gives the current usage; [validation](validation.md) distinguishes package execution from those remaining obligations.

Cordis.NET targets the pinned DeepSeek Harness vendored Cordis behavior described in [upstream](upstream.md). Compatibility is assessed per observable contract, not by package name or test count alone.

## Upstream fidelity requirement

Cordis.NET is a faithful, idiomatic .NET port of the fixed DSH baseline and the repository's agreed generic application infrastructure. Its own experimental designs do not establish a separate framework specification or a permanent compatibility obligation. The normative sources are the fixed upstream behavior, the agreed repository scope, and .NET adaptations supported by a concrete platform need.

Current code, API snapshots, generated clients and tests must be corrected against those sources. A signature's presence on main, an earlier public release or a passing old test does not by itself justify preserving an incorrect port. Correct errors and migrate their consumers directly. Retain a compatibility route only when an independent consumer or compatibility commitment requires it. Protect persisted data and Git history separately from obsolete runtime interfaces. This policy does not require line-by-line TypeScript translation or authorize rewriting mechanisms that already satisfy their contract.

Upstream fidelity is a project compatibility requirement. Evaluate changes against the fixed DSH revision in `upstream.lock.json`, its actual production callers, and their observable behavior. Check timing, ownership, lifecycle, failure and recovery boundaries, including the caller's use of the underlying mechanisms. Classify every difference as a necessary platform adaptation or an explicit project decision, and provide focused evidence for that difference. Passing tests that only establish a wrapper's internal consistency cannot, by themselves, demonstrate upstream fidelity.

Deployment generations accept explicit external linked roots alongside the existing package and local maps. HMR awaits candidate lifecycle settlement, which may leave a fiber Pending until its services appear. Activation failure attempts recovery only after candidate cleanup has succeeded; secondary cleanup, recovery, and diagnostic observer failures do not replace the original error. Retained configuration references freeze at their generation's last committed value, while replacement and recovery fibers receive fresh references. A reference whose generic value type belongs to a collectible bundle can retain that bundle until the host releases the reference. CLR bundles resolve private managed dependencies within their stable artifact directories or explicitly requested development copies, or through explicitly shared host contracts; an unrelated default-context assembly cannot satisfy a missing private dependency. Framework assemblies still use the runtime, and native-library lookup retains the CLR/OS loading rules.

The 2026-10-09 replacement safety repair deliberately adapts the fixed DSH HMR warning-and-continue path. Ordinary `Fiber.DisposeAsync` still reports failures and continues sibling cleanup, with the existing effect-local group semantics. `Fiber.CleanupErrors` records cleanup failures, including previously removed effects and owned child fibers; failures remain recorded across restarts because the escaped work may still exist. Replacement refuses candidate activation after any old-generation cleanup failure. The original thrown exception carries `PluginReplacementFailure` phase, cleanup errors and `NotAttempted`/`Succeeded`/`Failed` recovery details. Unconfirmed candidate cleanup prevents V1 recovery; unsuccessful V1 recovery stops the partially restored fibers. `Succeeded` means candidate cleanup and active original-fiber settlement were confirmed by the framework, not proof that arbitrary business side effects were reversed. Diagnostic observer failures cannot turn a failed replacement into success.

Replacement requests disposal and independently waits for the captured fibers' lifecycle settlement, following fixed HMR's `registry.delete` followed by `fiber.await`. Repeated disposal of a non-root owned fiber remains single-shot; it does not prove earlier cleanup has finished. During failed-candidate retirement, `WaitAsync` can rethrow the retained startup error after reaching Disposed; that known startup error is distinct from a cleanup failure, as in upstream's `allSettled` recovery path. Cleanup failures recorded during the wait still prevent candidate commit or V1 recovery.

The supported online class is contract-compatible plugins whose owned work stops cooperatively. The application owns compatibility admission, closing new business admission before retirement, draining accepted work, and fencing retained callbacks, events and late commits. A refusal before retirement may preserve V1; a retirement failure can leave it partially stopped and must not be described as an unchanged graph. Unless actual V1 business readiness and failed-V2 retirement are verified, the application must keep the affected scope closed and invalidate late business authority. Missing failure details on an arbitrary resolver callback also provide no recovery guarantee. `Context.DisposeAsync`, an old resolver mapping, an unload request or a live/collected ALC alone proves none of these business outcomes. Complete online package Update and concurrent update transactions are outside this replacement repair; the separate package installation path below supports updates that take effect after restart; [validation](validation.md) records the real Host fixture and the remaining limits.

The Host fixture checks plugin readiness while affected business admission remains closed and calls plugin code without holding the admission lock. For V2, admission opens only after the entire resolver replacement returns successfully and commits its mapping. For recovered V1, the resolver must finish its failed-candidate rollback before business validation and reopening; the original replacement error is still rethrown. These are application-owned operations, not a new production readiness API. If business validation fails after Loader has switched successfully, resolver callback failure retains the old mapping but cannot restore the old graph. The fixture explicitly marks that scope as requiring intervention, keeps HTTP/callback/event business closed, and refuses subsequent replacement, including callers already queued. It does not claim V1 recovery or automatically repair the split. A real application must implement the same closed-state responsibility or a separately proven recovery before resuming.

Concurrent Host replacements require application-owned coordination across the entire replacement, including readiness validation and reopening or failure closure after the resolver returns. The fixture uses one asynchronous update lock for that scope. The resolver serializes its own mutation; it does not serialize the application's later admission decisions. This coordination does not implement a complete package Update transaction.

Cooperative unload observer errors are exposed as text snapshots in `ClrUnloadObservation.UnloadError`, without retaining the exception instance or its collectible type. `UnloadRequested` records an attempt; `IsCollected` observes the managed load-context wrapper. An `Unloading` handler that throws can interrupt physical release even after that wrapper is collected, leaving DLLs locked. The host must repair or remove the failing handler and explicitly request `Unload()` again while it still holds the actual context; the adapter does not retry automatically. Physical deletion is a separate result and can remain blocked by retained references or interrupted release.

The [CLR artifact workflow](clr-artifacts.md) uses stable directories by default. The toolchain moves completed work output once, keeps its integrity receipt outside the approved artifact tree, verifies on startup and retains files after logical removal. ALC creation does not copy the artifact; ALC collection does not authorize deleting it. Explicit `ShadowCopy` remains available for quiescent development outputs that must later be rebuilt in place. Native static-state isolation per ALC is not promised. Existing deployments without a receipt require explicit reinstallation; they are not silently resealed.

Patch source loading, field editing and Settings attribution treat falsey `insert` values (including `null` and `false`) as ordinary overrides, following the pinned Include application rule. The pinned ConfigEditor instead uses undefined or field-presence checks; inheritance restoration here deliberately follows Include so returning to the inherited configuration removes the effective override and permits later base updates. Real inserts, unrelated fields and source comments retain the existing editing contract.


The optional NuGet toolchain binds approval to the inspected root archive and executes an SDK preparation using only host-selected sources. Approval covers the whole MSBuild invocation, including dependency targets; it is not a per-dependency hash approval system or a sandbox. A successor refuses an unresolved run record until the old group is explicitly stopped and its termination confirmed. Retained or ambiguous records require explicit recovery; diagnostics preserve the actual stage and residual directories. ## Evidence

Config-watch registration uses the nearest existing canonical parent, following the pinned HMR watcher. When the target parent already exists, native observation excludes its subdirectories, matching DSH depth zero; unrelated SDK work subdirectories must not enter that watch's event buffer or metadata resolution. If ancestors are missing, FileSystemWatcher requires recursive observation: its boolean depth cannot exactly express DSH's bounded positive depth, so that broader native boundary remains explicit. A native buffer overflow preserves the original warning/error and queues a normal serialized refresh to recover lost notifications. This is a necessary FileSystemWatcher adaptation; pinned DSH only warns on runtime watch errors. Other native errors retain their diagnostics, and closed watches accept no new refresh.

Config-watch event delivery first matches the normalized event path, as in the pinned HMR watcher. Matching changes, deletion and ancestor creation queue refresh without reading the changed file's metadata. Native alias resolution remains a fallback; a failure reports the original exception through the existing warning/error channels and leaves later events usable. Each rename path is handled separately. Initial registration still rejects inaccessible paths, and closed watches ignore queued events.

Profile installation now rejects stale captured inputs with `profile-conflict` instead of saving the manifest read before preparation over a later edit. This is a native adaptation: the pinned DSH success path re-reads in `selectBundle`, but does not supply a product-wide candidate approval contract. Neither implementation guarantees conditional replacement against arbitrary editors that ignore the cooperative lock.

`PluginConfigurationOperations.AdmitProfileAsync` receives the library's immutable manifest text and raw root configuration candidate, composed through the existing Profile/Include machinery. A detached composition view cannot change the saved candidate. Installation and bundle selection admit before publication/persistence and apply that candidate through `ProfileSession`; removal admits its durable steps separately, including dependency removal before the tool releases its runtime mapping. CLR artifacts are retained and reported separately until explicit offline deletion. Refusing that second step leaves the package installed and deselected. Repeated selection still admits before reapplication. Ordinary consumers may omit admission. Existing hosts using only `ReconcileAsync` retain that callback when admission is absent; product admission requires candidate-aware reconciliation rather than silently reverting to a fresh disk composition.

Captured base changes also enter the existing Include update when the owner configuration compares equal; unchanged entries keep their fibers. Candidate callbacks are associated with the legacy callback present at assignment. A host that later replaces only `ReconcileAsync` retains that customization without admission; admission refuses until the host explicitly assigns candidate-aware reconciliation for that wiring.

The read set captures the complete profile manifest, base configuration, selected bundle manifests/patches, profile/home patches, compatibility input, launch overlays and deployment mappings. Preparation captures the prepared tree's relative file names and content hashes. Its declared `PublicationDirectory` permits that tree to move unchanged and a new identity's local mapping to be added. An update preserves the existing live mapping while the candidate composes against the prepared version; unrelated mappings and sources remain unchanged. The approved manifest replacement is another planned write. These transitions are distinguished from conflicts, including after publication. A post-publication conflict can report installed=false, selected=false, failed and a retained deployment directory when no dependency was saved; a later application failure can leave selection saved. No automatic merge, replay or whole-runtime rollback is introduced. Existing cancellation, installation waiting and toolchain ownership remain in force.

Online metadata editing uses `ReadProfileAsync` and `SaveProfileMetadataAsync` on the same owner. Saving waits for existing mutations, then checks the original revision; it cannot alter management-owned dependencies or `dsh` policy/selection. The host decides how to present waiting, drafts and conflicts. This is not consent on behalf of a product to restrict its authoring experience. Low-level `PackageManifest.Write` and static maintenance helpers still require caller-owned exclusion or an offline profile. All supported concurrent writers must follow the same profile lock protocol and queue ordering. Fingerprint checks detect observed changes; they do not close the final comparison-to-rename race against nonparticipating writers. Product-owned policy inputs and later runtime/plugin effects are not a new global transaction. A subsequent coordinated request is separate from the installation commit and may legitimately produce a different profile.

The latest completed run is summarized in [validation](validation.md). `docs/upstream-tests.json` is the immutable candidate inventory; `docs/test-map.json` contains current dispositions; `docs/scenario-map.json` records differential scenarios. Upstream source execution, .NET tests, paired traces, and manual assertion review remain separate evidence categories.

### CLR module identity and ownership

Pinned Loader module imports and default-export normalization select plugin entries independently of service `Provide`. Native adaptation uses explicit CLR entry types: legacy root `assembly`/`entryType` metadata remains valid, and optional `exports` maps package subpaths to entry types in the same assembly. Requests with one normalized bundle directory share a physical loading mode, assembly identity and collectible load context. Stable loading retains the original files; explicit ShadowCopy shares one development copy. Mixing load modes for entries of one loaded bundle is refused before importing the additional entry. Resolver leases are per request, while lifecycle and configuration remain per Loader Fiber. Final lease removal requests unload; retained references and unload observer failures can delay collection or shadow deletion. Core, Clr and Composition are shared contract assemblies by default; additional contracts require explicit host selection. Private dependencies cannot be satisfied by an unrelated default-context assembly.

The group `ClrModuleResolver.ReplaceAsync` overload requires every registered request of the bundle, including aliases and unloaded exports. ### Native Typert contracts and carrier

The continuation supplies a Roslyn author generator, compiler-independent descriptors, System.Text.Json metadata codecs and schemas, a Fiber-owned registry, explicit artifact-resolver Loader integration, a Gateway, and generated TypeScript module/declaration artifacts. The generator is delivered in `Cordis.NET.Composition`'s analyzer directory. This covers declared native Remote boundaries; it does not reproduce the pinned TypeScript compiler's complete source type graph. Explicit JSON metadata and its naming, member-nullability and required-field options define the native data contract. Roslyn supplies erased root nullable reference annotations through `TypertCodec.CreateNullable`; its nullable schema projection preserves non-null recursive children. Results retain the pinned invocation behavior without added schema admission. See [authoring](authoring.md#module-exports-and-generated-remote-contracts-2026-10-09) for public declarations and package consumers.

`IClrTypertModule` exports contributions from the same loaded CLR bundle as its plugin factory. Typert imports are cached for the owner Fiber's activation. At a dynamic module-generation boundary, suspend the affected exact Loader requests after candidate preparation and before retiring their providers. Resume only after route commit or confirmed old-provider recovery. Suspension withdraws those registrations, invalidates their artifact caches and detaches old imports; other contributors keep their registration identity and owner. A late old import cannot register into the resumed generation. This releases the loader's references to old generated delegates and CLR serialization types; retaining an old contribution is not compatible with substituting a new assembly merely because its type names match. Registration validity also fences old invocations after withdrawal. Registry metadata does not replace Cordis service authority or product policy.

The Gateway supports direct calls, registered Context selection/object lookup, Remote errors, cooperative cancellation and downlink streams. ASP.NET uses the shared Host Connection, fixed unary envelope, text WebSocket mux and unary multipart results. Generated clients borrow the shared Connection; `mountRemote` registers disjoint methods under the existing owner and shared root namespace. This local implementation does not complete reverse Context, owned values or full event semantics.

Host unary cancellation follows the pinned invocation boundary: a successful business call is not rejected solely because its carrier signal is aborted, while a business failure under an aborted signal becomes `gateway/cancelled`. Downlink reads race the signal and finish cleanup before exposing a failure. The native enumerator must settle an outstanding read before disposal; late read errors are observed without replacing cancellation, and disposal errors remain cleanup failures. Neither the pinned Host nor this adapter promises forced termination of an unbounded business call or cleanup. Provider/definition withdrawal fences are a separate native generation adaptation, not an upstream active-call abort mechanism.

Client installation serializes namespace mutations and waits for same-name provider retirement outside that queue, so dependency cleanup can progress. Duplicate methods are refused before publication. A synchronous `internal/service` observer that throws during publication retains the fixed Cordis provider's failure behavior: it can leave a provided namespace even though mounting rejects. The adapter does not promise arbitrary observer rollback; repair that observer and retire its owner before retrying.

### Open closure and evidence boundaries

The subsequent quality repair preserves each main assembly's dependency root in a shared CLR bundle and rejects conflicting private binaries, rather than relying on the first entry's resolver or the CLR's loaded-assembly cache. Byte-identical copies can share identity. This explicit .NET policy does not derive an upstream ABI compatibility algorithm. Native schema projection also preserves positional tuple contracts instead of discarding `prefixItems`; unsupported length constraints reject generation. These repairs do not add full source analysis.

Provider generation checks are verified independently of definition withdrawal: pending unary Service, lookup, Context and downlink operations retain active descriptors while their providers are replaced. Withdrawal alone does not abort those operations; old successful results fail the native generation check. JSON codec input validation, result serialization and stream cleanup limits are documented separately in the public API and [authoring guide](authoring.md). Read the latest validation record for the exact repaired source and package checkpoints; earlier platform results apply to their recorded checkpoint.

Service validity uses the existing Core registration identity and its original, untraced provider value. A caller-bound view is the invocation receiver; a fresh view from each `Service<TState>.CreateView` does not invalidate a live provider. Admission captures the registration and raw value before contextual tracing. Each later check performs the normal contextual lookup before reading the final registration and raw value, so synchronous reentry cannot hide a changed provider. Reproviding the same object, including within the same Fiber, creates a different registration and invalidates an earlier admission. Setting a different raw value also invalidates it without replacing the registration; same-value `Set`, ordinary `Notify` and changes in an unrelated isolated realm preserve it. These observations are internal to Core and Composition; they add no public API, service registry or persistent generation state. A pending call can retain its registration and provider until it settles, within the existing cooperative CLR lifetime boundary.

Complete source type analysis, rich Context/owned-value graphs, full Peer/waterfall events and the remaining rich-value semantics remain unimplemented. The shared Connection entry below records the current text mux, typed uplink and unary multipart boundaries. Standard Settings, PluginManager and host-selected emit notifications now use generated contracts. Native state, raw configuration, artifact routes and the independent `MapCordisService` adapter retain their own duties. The [independent multi-entry package consumer](../scripts/verify-clr-multi-entry.py) has local ordinary-runtime and generated TypeScript/HTTP evidence for shared bundle identity, configuration, HMR recovery/replacement, provider/contract withdrawal and stale invocation rejection. The separate [native Remote package consumer](../scripts/verify-typert.py) exercises additional boundaries. ## Independent native model and Settings boundary, 2026-10-10

The source compiler emits the current declaration artifact before runtime descriptor emission. It retains method/parameter names, referenced types, member and constructor relationships, C# required and JSON-required facts, nested null annotations, supported constants, optional argument defaults, documentation, JSON policies and the four STJ null-state annotations. Effective compiler settings are recorded. Artifact identity identifies those facts, not activation, correspondence to an arbitrary DLL or a universal replacement admission decision. Roslyn symbols are extraction inputs; the serialized model contains no symbols, CLR Types, delegates or JsonTypeInfo instances. Referenced CLR declarations retain metadata provenance; metadata does not supply every source-only fact.

Runtime descriptors and `TypertTypeModel` are derived outputs, not sources for reconstructing declarations. The current contract has one public artifact, `cordis/typert/$(AssemblyName).cordis.model.json`, and one `extract-model` entry combining ordinary roots and service selection. Selected-service drift checks remain required, while the separate wire artifact and its conformance bridge are retired. Internal projections must be recomputable from declaration facts and explicit backend policy, not a second saved authored model. See the [stage contract](development.md#model-pipeline-contract) for owners and exit paths.

The .NET emitter currently projects direct unary methods, downlink streams and selected ordinary data records/classes. Actual coverage includes booleans, strings, integers, arrays, read-only list interfaces, JsonElement, nullable members, required constructors/init members, naming/ignore policies and selected null-state annotations. Read-only data members, record structs, data inheritance, polymorphism/custom converters and richer Remote shapes are retained or diagnosed and refused by this projection. No complete C# or TypeScript type-system equivalence is claimed. JSON policy cannot omit required carrier argument fields, including explicit null or default values.

Constant projection preserves nullable primitive numeric initializers, including float and decimal literal suffixes, and explicit null. This does not change the model format. Before writing caller source, the emitter checks all projected DTO and generated client, JSON context, failure and method-envelope type names in the target namespace. A collision is refused with both origins identified; refusal removes the owned stale output instead of deferring the conflict to C# compilation.

The generated client reuses the native HTTP result envelope and RemoteError. Its DTO/throwing API is a .NET adaptation; TS remains an independent output with its existing result API and carrier. The compiler uses only selected-SDK Roslyn, STJ and existing framework transport; no new NuGet dependency is selected here.

Settings describe exposes selected live configuration through the existing profile queue, Include and schema/redaction helpers.
