# Compatibility and evidence

[中文](compatibility.zh.md)

Cordis.NET targets the pinned DeepSeek Harness vendored Cordis behavior described in [upstream](upstream.md). Compatibility is assessed per observable contract, not by package name or test count alone.

## Upstream fidelity requirement

Upstream fidelity is a project compatibility requirement. Evaluate changes against the fixed DSH revision in `upstream.lock.json`, its actual production callers, and their observable behavior. Check timing, ownership, lifecycle, failure and recovery boundaries, including the caller's use of the underlying mechanisms. Classify every difference as a necessary platform adaptation or an explicit project decision, and provide focused evidence for that difference. Passing tests that only establish a wrapper's internal consistency cannot, by themselves, demonstrate upstream fidelity.

## Status vocabulary

- **Implemented:** the .NET behavior exists.
- **Executed:** a named .NET test, upstream source test, or paired scenario ran.
- **Assertion reviewed:** the upstream setup, helpers, and assertions were individually matched or given an explicit adaptation.
- **Not supported:** the behavior is outside the product or platform boundary.

The immutable historical inventory targets DSH `ddefc45fbc7f8e46dd73185e68295696d1297887` and contains 631 upstream candidate instances. It does not describe assertion closure for the new baseline. The current upgrade scope, behavior mapping and platform adaptations are recorded in [the upgrade matrix](upgrade-0.2.0-rc.2.md). Current disposition records 323 as implementation complete. Of those, 36 have a complete assertion review and 287 have not received a complete assertion review. The remaining 308 are explicitly non-complete, usually because they concern JavaScript or DeepSeek Harness product behavior outside Cordis.NET. These figures do not claim a compatibility percentage.

## Deployment boundaries

The optional browser module bootstrap forwards shell-owned `staticModules` and optional `loadBundle` to the fixed DSH module system. Native catalog capture accepts the same additional exact request names; SDK defaults remain available. A package root does not supply arbitrary subpaths. The shell owns objects and types, while Cordis owns plugin effects. Default and custom transports retain the existing same-origin revision boundary. This restores the upstream bootstrap seam without adding a module registry or npm resolver; see [development](development.md#shell-owned-client-modules).

Browser startup reuses the fixed web activation audit; later sync retains diagnostic/retry semantics. HTTP/SSE recovery reuses the fixed connection controller with a numeric timing adapter instead of the Schemastery runtime. Transient connection loss preserves plugins; explicit close withdraws them. CLI arguments, readiness and bounded exit reuse Composition, ProfileSession and Generic Host. These restore upstream assembly responsibilities without changing Core Pending semantics.

| Path | Supported behavior | Boundary |
|---|---|---|
| Static Core and Composition | JIT and Native AOT; static module registration, lifecycle, configuration, profiles and selected extensions | New plugin code requires republishing the application |
| CLR adapter | Runtime loading, replacement, rollback, and cooperative unload of managed assemblies | Ordinary runtime only; retained CLR references can prevent collection |
| JavaScript adapter | Actual `!!js` evaluation and a controlled context bridge through Jint | Trusted configuration only; no Node module environment, sandbox, or Native AOT claim |

Cordis.NET does not execute arbitrary server-side TypeScript plugins. JavaScript prototypes, thrown primitives, cyclic object graphs and Node resolution are not general platform compatibility promises. Agent/LLM business behavior, RSI goals and FSM domain logic belong to products. Reusable client/UI, diagnostics and installation mechanisms remain repository scope; their protocols and Node implementations require explicit adaptations above Core. A historical inventory describes its recorded coverage, not permanent repository exclusions. An in-scope gap is not an available feature.

`ConfigObject<T>` is a Composition authoring adapter over the existing `ConfigSchema<T>`, not a second validator. It combines explicit complete data-field projections into live bindings, strict ordinary comparison and complete persistence. The author retains responsibility for defaults, validation, raw round trips and complete field coverage. This API requires `0.2.0-alpha.3` or later; it is not available in the published `0.2.0-alpha.1` packages.

Field editing reuses fixed ConfigEditor responsibilities: ownership, normal hooks/validation, complete raw user overrides, overlay refusal, durable write and cooperative recovery. It keeps YAML flow roots when needed to preserve unrelated comments. Revisions are native content/activation hashes; non-round-trippable `Undefined` SET values are refused without changing runtime sentinel semantics. Deployment restart requirements refuse edits before persistence. Settings selects declared live data, including nested objects and collections, and enforces host selection/redaction on submission too. User-source presence includes uniquely inserted source rows as an explicit native adaptation; it is not inferred by comparing effective values. Ordered SET/reset requests validate one complete candidate before writing. Explicit metadata supports separate Schemastery and JSON Schema projections; arbitrary validator transforms cannot be inferred, and projection diagnostics remain part of the contract. Core stores annotations without interpreting form policy. Independent review and combined validation results are recorded in [validation](validation.md).

Client artifacts reuse `dsh.client.platform=web` and `exports['./client']` through deployment package routing. Canonical containment covers directory links. The original Probes consumer retains self-contained ESM and polling. Current source also supplies `ClientModuleCatalog` and an optional TypeScript package using the fixed Cordis/Loader, module entries and SlotCore mechanisms. Its explicitly declared external packages are compiled into lazy factory registrations; it does not promise arbitrary npm resolution. HTTP/SSE management is a native protocol with host authorization, generation fencing and active installation queries, not wire compatibility with arbitrary Typert services. Source tests, browser interaction, CLR execution and package consumers remain distinct evidence. These additions do not change the formal behavior lock or the published batch.

Deployment generations accept explicit external linked roots alongside the existing package and local maps. A generation captures each link's canonical target; removing a root stops routing its importers without unloading retained modules. Re-adding that name with another target requires a restart, including after an intervening removal. Linked peers are read from current ancestor manifests; private lookups remain host-provided, and CLR exports remain explicit mappings. This does not install a Node loader or emulate Node exports, package self-references, CommonJS/ESM differences, or worker propagation.

HMR awaits candidate lifecycle settlement, which may leave a fiber Pending until its services appear. Activation failure attempts recovery only after candidate cleanup has succeeded; secondary cleanup, recovery, and diagnostic observer failures do not replace the original error. Retained configuration references freeze at their generation's last committed value, while replacement and recovery fibers receive fresh references. A reference whose generic value type belongs to a collectible bundle can retain that bundle until the host releases the reference. CLR bundles resolve private managed dependencies within their stable artifact directories or explicitly requested development copies, or through explicitly shared host contracts; an unrelated default-context assembly cannot satisfy a missing private dependency. Framework assemblies still use the runtime, and native-library lookup retains the CLR/OS loading rules.

The 2026-10-09 replacement safety repair deliberately adapts the fixed DSH HMR warning-and-continue path. Ordinary `Fiber.DisposeAsync` still reports failures and continues sibling cleanup, with the existing effect-local group semantics. `Fiber.CleanupErrors` records cleanup failures, including previously removed effects and owned child fibers; failures remain recorded across restarts because the escaped work may still exist. Replacement refuses candidate activation after any old-generation cleanup failure. The original thrown exception carries `PluginReplacementFailure` phase, cleanup errors and `NotAttempted`/`Succeeded`/`Failed` recovery details. Unconfirmed candidate cleanup prevents V1 recovery; unsuccessful V1 recovery stops the partially restored fibers. `Succeeded` means candidate cleanup and active original-fiber settlement were confirmed by the framework, not proof that arbitrary business side effects were reversed. Diagnostic observer failures cannot turn a failed replacement into success.

Replacement requests disposal and independently waits for the captured fibers' lifecycle settlement, following fixed HMR's `registry.delete` followed by `fiber.await`. Repeated disposal of a non-root owned fiber remains single-shot; it does not prove earlier cleanup has finished. During failed-candidate retirement, `WaitAsync` can rethrow the retained startup error after reaching Disposed; that known startup error is distinct from a cleanup failure, as in upstream's `allSettled` recovery path. Cleanup failures recorded during the wait still prevent candidate commit or V1 recovery.

The supported online class is contract-compatible plugins whose owned work stops cooperatively. The application owns compatibility admission, closing new business admission before retirement, draining accepted work, and fencing retained callbacks, events and late commits. A refusal before retirement may preserve V1; a retirement failure can leave it partially stopped and must not be described as an unchanged graph. Unless actual V1 business readiness and failed-V2 retirement are verified, the application must keep the affected scope closed and invalidate late business authority. Missing failure details on an arbitrary resolver callback also provide no recovery guarantee. `Context.DisposeAsync`, an old resolver mapping, an unload request or a live/collected ALC alone proves none of these business outcomes. Complete online package Update and concurrent update transactions are outside this replacement repair; the separate package installation path below supports updates that take effect after restart; [validation](validation.md) records the real Host fixture and the remaining limits.

The Host fixture checks plugin readiness while affected business admission remains closed and calls plugin code without holding the admission lock. For V2, admission opens only after the entire resolver replacement returns successfully and commits its mapping. For recovered V1, the resolver must finish its failed-candidate rollback before business validation and reopening; the original replacement error is still rethrown. These are application-owned operations, not a new production readiness API. If business validation fails after Loader has switched successfully, resolver callback failure retains the old mapping but cannot restore the old graph. The fixture explicitly marks that scope as requiring intervention, keeps HTTP/callback/event business closed, and refuses subsequent replacement, including callers already queued. It does not claim V1 recovery or automatically repair the split. A real application must implement the same closed-state responsibility or a separately proven recovery before resuming.

Concurrent Host replacements require application-owned coordination across the entire replacement, including readiness validation and reopening or failure closure after the resolver returns. The fixture uses one asynchronous update lock for that scope. The resolver serializes its own mutation; it does not serialize the application's later admission decisions. This coordination does not implement a complete package Update transaction.

Cooperative unload observer errors are exposed as text snapshots in `ClrUnloadObservation.UnloadError`, without retaining the exception instance or its collectible type. `UnloadRequested` records an attempt; `IsCollected` observes the managed load-context wrapper. An `Unloading` handler that throws can interrupt physical release even after that wrapper is collected, leaving DLLs locked. The host must repair or remove the failing handler and explicitly request `Unload()` again while it still holds the actual context; the adapter does not retry automatically. Physical deletion is a separate result and can remain blocked by retained references or interrupted release.

The [CLR artifact workflow](clr-artifacts.md) uses stable directories by default. The toolchain moves completed work output once, keeps its integrity receipt outside the approved artifact tree, verifies on startup and retains files after logical removal. ALC creation does not copy the artifact; ALC collection does not authorize deleting it. Explicit `ShadowCopy` remains available for quiescent development outputs that must later be rebuilt in place. Native static-state isolation per ALC is not promised. Existing deployments without a receipt require explicit reinstallation; they are not silently resealed.

Patch source loading, field editing and Settings attribution treat falsey `insert` values (including `null` and `false`) as ordinary overrides, following the pinned Include application rule. The pinned ConfigEditor instead uses undefined or field-presence checks; inheritance restoration here deliberately follows Include so returning to the inherited configuration removes the effective override and permits later base updates. Real inserts, unrelated fields and source comments retain the existing editing contract.


The optional NuGet toolchain binds approval to the inspected root archive and executes an SDK preparation using only host-selected sources. Approval covers the whole MSBuild invocation, including dependency targets; it is not a per-dependency hash approval system or a sandbox. Windows tool processes use Job-list creation (Windows 10 / Windows Server 2016 or later), record ownership before resuming, and require both process-tree and pipe settlement. Linux uses an isolated process group. Cancellation stops that group; abrupt host death may leave it running. A successor refuses an unresolved run record until the old group is explicitly stopped and its termination confirmed. Retained or ambiguous records require explicit recovery; diagnostics preserve the actual stage and residual directories. Updating an installed profile-owned NuGet package prepares and admits the new version, moves its complete output to a separate version directory, and records the version and selection for the next startup. It returns `restart-required` and leaves the live resolver route and plugin fibers on the old version, matching the pinned DSH installed-package boundary. Same-version installs and installation-owned package replacement remain refused. Existing destination directories are never overwritten; preparation, admission and publication conflicts detected before saving retain the prior saved version and report residual output. This is not a filesystem transaction or automatic cleanup of old versions. Retired identities still require a fresh resolver before reinstalling; static AOT applications republish code changes.

Known package declarations captured by inspection are admitted before SDK preparation, including disabled installations. `PackageInspection.ManifestJson` is an immutable snapshot from the same archive as its hash; adapters unable to inspect declarations may omit it and retain prepared-manifest admission. The .NET toolchain always captures the root declaration, checks the root archive before preparation and after restore, and retains prepared-manifest admission. Build approval does not grant a version exemption.

For a DSH-enabled NuGet host, explicitly set `ProfileLaunch.CompatibilityPackageName` to `DotnetPluginToolchain.NormalizeCompatibilityPackageName` and `ManifestLocator` to the toolchain's `LocateManifest`. This adapts only the grant key's name; exact package/runtime versions, manifest spelling and saved selections are preserved. Scoped npm names and the default DSH policy retain their existing rules. Management resolves a grant identity once before authorization and passes that canonical value unchanged to persistence; direct callers use `ResolveVersionExemptionIdentity` before `SetVersionExemptionAsync`. Grant changes participate in the existing DSH session refresh. Unreadable grant data remains non-authorizing and non-rewritable without aborting startup.

HTTP management authorizes the same endpoint-specific resource that it executes. Plugin/bundle enable uses `target`, removal and package inspection use `name`, active installation wait/cancel use `requestId`, and exemptions use the canonical `packageVersion`. Configuration/Settings use `entryId`; client artifacts use their package route. Extra fields cannot substitute another authorization target. Inventory and event streams require their operation-level permission with no individual resource.

The native management `Changed` event isolates each synchronous observer's failure and logs it without replacing a completed operation's result or preventing later observers. It does not alter Core's event semantics. Enablement and bundle selection persist before reconciliation; a failed application result can leave those files saved. Field-edit recovery retains its separate contract.

## Evidence

Profile installation now rejects stale captured inputs with `profile-conflict` instead of saving the manifest read before preparation over a later edit. This is a native adaptation: the pinned DSH success path re-reads in `selectBundle`, but does not supply a product-wide candidate approval contract. Neither implementation guarantees conditional replacement against arbitrary editors that ignore the cooperative lock.

`PluginConfigurationOperations.AdmitProfileAsync` receives the library's immutable manifest text and raw root configuration candidate, composed through the existing Profile/Include machinery. A detached composition view cannot change the saved candidate. Installation and bundle selection admit before publication/persistence and apply that candidate through `ProfileSession`; removal admits its durable steps separately, including dependency removal before the tool releases its runtime mapping. CLR artifacts are retained and reported separately until explicit offline deletion. Refusing that second step leaves the package installed and deselected. Repeated selection still admits before reapplication. Ordinary consumers may omit admission. Existing hosts using only `ReconcileAsync` retain that callback when admission is absent; product admission requires candidate-aware reconciliation rather than silently reverting to a fresh disk composition.

Captured base changes also enter the existing Include update when the owner configuration compares equal; unchanged entries keep their fibers. Candidate callbacks are associated with the legacy callback present at assignment. A host that later replaces only `ReconcileAsync` retains that customization without admission; admission refuses until the host explicitly assigns candidate-aware reconciliation for that wiring.

The read set captures the complete profile manifest, base configuration, selected bundle manifests/patches, profile/home patches, compatibility input, launch overlays and deployment mappings. Preparation captures the prepared tree's relative file names and content hashes. Its declared `PublicationDirectory` permits that tree to move unchanged and a new identity's local mapping to be added. An update preserves the existing live mapping while the candidate composes against the prepared version; unrelated mappings and sources remain unchanged. The approved manifest replacement is another planned write. These transitions are distinguished from conflicts, including after publication. A post-publication conflict can report installed=false, selected=false, failed and a retained deployment directory when no dependency was saved; a later application failure can leave selection saved. No automatic merge, replay or whole-runtime rollback is introduced. Existing cancellation, installation waiting and toolchain ownership remain in force.

Online metadata editing uses `ReadProfileAsync` and `SaveProfileMetadataAsync` on the same owner. Saving waits for existing mutations, then checks the original revision; it cannot alter management-owned dependencies or `dsh` policy/selection. The host decides how to present waiting, drafts and conflicts. This is not consent on behalf of a product to restrict its authoring experience. Low-level `PackageManifest.Write` and static maintenance helpers still require caller-owned exclusion or an offline profile. All supported concurrent writers must follow the same profile lock protocol and queue ordering. Fingerprint checks detect observed changes; they do not close the final comparison-to-rename race against nonparticipating writers. Product-owned policy inputs and later runtime/plugin effects are not a new global transaction. A subsequent coordinated request is separate from the installation commit and may legitimately produce a different profile.

The latest completed run is summarized in [validation](validation.md). `docs/upstream-tests.json` is the immutable candidate inventory; `docs/test-map.json` contains current dispositions; `docs/scenario-map.json` records differential scenarios. Upstream source execution, .NET tests, paired traces, and manual assertion review remain separate evidence categories.

## Module export and Typert continuation, 2026-10-09

The [scope reconciliation](development.md#application-infrastructure-scope-reconciliation-2026-10-09) records the starting-head omissions separately from this implementation. The behavior authority remains DSH `639ed015397290b3745d163aafe02ffee4aa3f84`. Earlier completion records and the pinned baseline are unchanged. This source continuation introduces no package publication claim.

### CLR module identity and ownership

Pinned Loader module imports and default-export normalization select plugin entries independently of service `Provide`. Native adaptation uses explicit CLR entry types: legacy root `assembly`/`entryType` metadata remains valid, and optional `exports` maps package subpaths to entry types in the same assembly. There is no new Core export table and no mandatory empty table for single-entry plugins.

Requests with one normalized bundle directory share a physical loading mode, assembly identity and collectible load context. Stable loading retains the original files; explicit ShadowCopy shares one development copy. Mixing load modes for entries of one loaded bundle is refused before importing the additional entry. Resolver leases are per request, while lifecycle and configuration remain per Loader Fiber. Final lease removal requests unload; retained references and unload observer failures can delay collection or shadow deletion. Core, Clr and Composition are shared contract assemblies by default; additional contracts require explicit host selection. Private dependencies cannot be satisfied by an unrelated default-context assembly.

The group `ClrModuleResolver.ReplaceAsync` overload requires every registered request of the bundle, including aliases and unloaded exports. It prepares one candidate generation and commits its routes together. `Loader.ReplacePluginsAsync` reuses existing Fiber settlement and recovery; Pending remains valid. The callback owns teardown and recovery. Atomic route publication does not imply rollback of candidate side effects or a product-wide transaction. Contract descriptors do not add a universal replacement admission algorithm.

### Native Typert contracts and carrier

The continuation supplies a Roslyn author generator, compiler-independent descriptors, System.Text.Json metadata codecs and schemas, a Fiber-owned registry, explicit artifact-resolver Loader integration, a Gateway, and generated TypeScript module/declaration artifacts. The generator is delivered in `Cordis.NET.Composition`'s analyzer directory. This covers declared native Remote boundaries; it does not reproduce the pinned TypeScript compiler's complete source type graph. Explicit JSON metadata and its naming, member-nullability and required-field options define the native data contract. Roslyn supplies erased root nullable reference annotations through `TypertCodec.CreateNullable`; its nullable schema projection preserves non-null recursive children. Results retain the pinned invocation behavior without added schema admission. See [authoring](authoring.md#module-exports-and-generated-remote-contracts-2026-10-09) for public declarations and package consumers.

`IClrTypertModule` exports contributions from the same loaded CLR bundle as its plugin factory. Typert imports are cached for the owner Fiber's activation. Dynamic HMR must retire that owner before provider replacement and restart it after commit, or after old-provider recovery on failure. This releases old generated delegates and CLR serialization types; retaining an old contribution is not compatible with substituting a new assembly merely because its type names match. Registration validity also fences old invocations after withdrawal. Registry metadata does not replace Cordis service authority or product policy.

The native Gateway supports direct calls, explicitly registered Context selection/object lookup, Remote errors, cooperative cancellation, downlink streams and JSON base64 byte results. Its ASP.NET carrier is HTTP JSON/NDJSON with host-supplied endpoint authorization. Generated TypeScript `createRemote` consumes that carrier; asynchronous `mountRemote` awaits owner registration and aggregates disjoint methods into a shared root `remote.<namespace>` service, with contribution-specific withdrawal. These are explicit platform adaptations, not a claim of the entire fixed Typert wire protocol.

Host unary cancellation follows the pinned invocation boundary: a successful business call is not rejected solely because its carrier signal is aborted, while a business failure under an aborted signal becomes `gateway/cancelled`. Downlink reads race the signal and finish cleanup before exposing a failure. The native enumerator must settle an outstanding read before disposal; late read errors are observed without replacing cancellation, and disposal errors remain cleanup failures. Neither the pinned Host nor this adapter promises forced termination of an unbounded business call or cleanup. Provider/definition withdrawal fences are a separate native generation adaptation, not an upstream active-call abort mechanism.

Client installation serializes namespace mutations and waits for same-name provider retirement outside that queue, so dependency cleanup can progress. Duplicate methods are refused before publication. A synchronous `internal/service` observer that throws during publication retains the fixed Cordis provider's failure behavior: it can leave a provided namespace even though mounting rejects. The adapter does not promise arbitrary observer rollback; repair that observer and retire its owner before retrying.

### Open closure and evidence boundaries

The subsequent quality repair preserves each main assembly's dependency root in a shared CLR bundle and rejects conflicting private binaries, rather than relying on the first entry's resolver or the CLR's loaded-assembly cache. Byte-identical copies can share identity. This explicit .NET policy does not derive an upstream ABI compatibility algorithm. Native schema projection also preserves positional tuple contracts instead of discarding `prefixItems`; unsupported length constraints reject generation. These repairs do not add full source analysis.

Provider generation checks are verified independently of definition withdrawal: pending unary Service, lookup, Context and downlink operations retain active descriptors while their providers are replaced. Withdrawal alone does not abort those operations; old successful results fail the native generation check. JSON codec input validation, result serialization and stream cleanup limits are documented separately in the public API and [authoring guide](authoring.md). Read the latest validation record for the exact repaired source and package checkpoints; earlier platform results apply to their recorded checkpoint.

Complete source type analysis, rich Context/owned-value graphs, Peer/uplink/multiplexed streams and event remotes, and the complete binary attachment protocol remain unimplemented. Migration of PluginManager, Settings/configuration and client management production consumers to generated contracts remains open. Existing configuration schema exports, handwritten `MapCordisService` and HTTP/SSE management retain their current contracts; they do not count as completed Typert consumers.

The [independent multi-entry package consumer](../scripts/verify-clr-multi-entry.py) has local ordinary-runtime and generated TypeScript/HTTP evidence for shared bundle identity, configuration, HMR recovery/replacement, provider/contract withdrawal and stale invocation rejection. The separate [native Remote package consumer](../scripts/verify-typert.py) exercises additional boundaries. Windows/Linux, JIT and static Native AOT results must be read separately from the latest completed [validation](validation.md); ongoing runs and existing source tests are not formal platform acceptance. Dynamic CLR loading has no Native AOT claim.

Product replacement acceptance, business retirement/draining, permissions, Project authority, basis and receipt/outbox rules remain product-owned. No application `ApiCatalog` standard or competing overall plan is introduced. The remaining generic gaps stay recorded in the original application infrastructure scope.
