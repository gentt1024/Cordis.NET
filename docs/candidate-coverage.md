# Candidate capability coverage

[中文](candidate-coverage.zh.md)

This index follows the C01–C22 capability identifiers in the 2026-10-22 upgrade investigation. The candidate is DSH `687f282e8625c6b8d11ff58211a90524be2e4317`; Core/Loader source origin is `56b3d4f725681cf4556c1a8695a709cc3b6eed74`. The formal [behavior lock](../upstream.lock.json) remains `639ed015397290b3745d163aafe02ffee4aa3f84`. S1–S9 are scoped candidate adaptations, not a baseline promotion.

Each row identifies implementation and checks that exercise a capability. It does not assert that every upstream setup, helper or assertion has been individually matched. “Implemented”, “executed” and “assertion reviewed” retain their separate [compatibility meanings](compatibility.md#status-vocabulary). The immutable [historical inventory](upstream-tests.json) and its existing dispositions are unchanged. Passing upstream source cases establishes source execution; passing a native consumer establishes that consumer's contract. Neither alone proves complete assertion equivalence.

The bounded [candidate delta review](candidate-delta-review.json) links changed contracts to exact upstream case identities and named native assertions. It records setup/helper assumptions and native adaptations. The discovery gate checks candidate source blobs and native file hashes before publishing the mapping receipt. Formal-baseline blobs record the reviewed Git comparison; the discovery checkout does not need that older history. A reviewed contract does not mark every assertion in its source file, or the whole candidate inventory, as ported. Execution remains a separate receipt bound to the frozen commit.

## C15 retained backend refusals

The [backend disposition table](development.md#alpha5-independent-backend-disposition) remains authoritative for independent saved-model DTO/STJ and Web generation. Closed authored generic DTO substitution; inheritance flattening and polymorphic discriminator projection; nested DTO naming, non-string dictionary keys and multidimensional arrays; saved Web binary-attachment metadata; and unsupported read-only/extension-data/non-public serializer shapes are not closed by S8's metadata API. Arbitrary converters, accessor/constructor business and non-constant initializers cannot be reconstructed from saved facts. Missing source-reference models and conflicting JSON policies remain explicit errors. Actual Host STJ binding is a separate capability.

The [named integration boundaries](development.md#remaining-support-boundaries) also remain: WPF, Avalonia, Godot .NET and Blazor need their own evidence; Rider does not establish other IDE behavior. These are retained support obligations and limitations, not removed scope or new candidate regressions.

## S10 execution and promotion boundary

The S10 candidate source gate discovers and records a new path-independent case inventory from fixed Git blobs, preserves duplicate parameterized titles with ordinals, runs four shards per platform and requires an exact union. Its manifest/counts and receipts remain separate from the historical inventory. The source suite scope is an execution boundary, not an automatic native assertion mapping. Deliberately skipped source files and the filesystem-capability skip remain visible.

When candidate validation is requested, [the runtime gate](../scripts/verify.py) compares the candidate's established and upgrade traces directly with the same in-memory native JIT outputs, then retains JIT/AOT parity. [CI](../.github/workflows/ci.yml) also requires formal-lock runtime/source gates and the candidate source union. The [portable runner](../scripts/verify-portable-authoring.py) consumes the exact Linux-produced package/runtime/tool bytes on Windows, Linux and macOS; Windows/Linux additionally exercise CLR deployment/multi-entry and static package callers with AOT. macOS authoring/browser/native consumer evidence does not become full macOS runtime or AOT acceptance.

Execution results belong to the final frozen source/package receipts and [validation record](validation.md). This index records no pending run as passed and authorizes no release or baseline change. Promotion still requires review under [updating the behavior target](updating-baseline.md), including the retained capability limits above.
