## Fast loop

The package version for source builds is defined once in [Directory.Build.props](../Directory.Build.props). Projects inherit it; package verification scripts read it for their isolated consumers. When an exact local package version is needed, query that same value:

```console
dotnet msbuild src/Cordis.Core/Cordis.Core.csproj -getProperty:Version
```

Ordinary commits do not require a package version bump. The source version does not establish NuGet availability; use the [installation guide](getting-started.md) for published packages and the [authoring guide](authoring.md) for authoring API availability and source examples.

Third-party dependency versions are declared in [Directory.Packages.props](../Directory.Packages.props); projects keep their own `PackageReference` items and metadata. Each project's `packages.lock.json` records its resolved dependency graph, and validation continues to use `--locked-mode`. Transitive pinning is not enabled. SDK-provided implicit packages remain controlled by the selected SDK.

```console
dotnet restore Cordis.slnx --locked-mode
dotnet build Cordis.slnx -c Release --no-restore
dotnet test Cordis.slnx -c Release --no-build
python scripts/check-docs.py
```

```console
python scripts/verify.py --dsh ../dsh-reference --origin ../upstream-cordis --aot --package --package-output artifacts/upgrade-packages

```

The full gate checks the locked SDK and dependencies, analyzers, tests, upstream source execution, differential scenarios, Native AOT, API shape, packages, and isolated consumers. Run it on Windows x64 and actual Linux x64 for release candidates. Generated outputs and raw logs may contain local paths or user names. Keep them outside the public tree; commit only redacted summaries and stable machine-readable evidence.

## Shell-owned client modules

The optional [browser module package](../clients/modules/README.md) exposes the fixed DSH static module table and optional transport through its public bootstrap. The shell owns shared module objects; plugin effects remain owned by Cordis.

```js
import { bootClientModules } from '/client-runtime/client.mjs'
const shell = { name: 'application shell' }
const tools = { format: value => String(value) }
const modules = await bootClientModules({
  graph: await fetch('/client/graph').then(response => response.json()),
  staticModules: { '@my-app/shell': shell, '@my-app/shell/tools': tools },
})
```

On the native Host, pass those same names to the additional `ClientModuleCatalog.CaptureAsync` overload through `platformModules: ["@my-app/shell", "@my-app/shell/tools"]`. Host declaration and browser supply must agree. Plugin authors list their exact imports in `dsh.client.external`; a root request does not supply subpaths. The author build bundles undeclared ordinary dependencies instead of implicitly making their subpaths external. The shell supplies types and module values; neither catalog nor bootstrap discovers npm packages.

`staticModules` extends the SDK defaults, with explicit keys taking precedence. Values are retained without cloning and survive plugin withdrawal/reload. Use the SDK's runtime instance for Cordis-related services. Optional `loadBundle(url)` must execute factory registration before resolving; the fixed script-element transport remains the default. Both transports receive the validated same-origin revisioned URL. Disposal releases plugin effects and the page facade, not shell objects.

The existing verification flow runs `verify-client-shared-modules.mjs` through the built public package with an independent plugin and injected Node transport. The existing browser carrier's `/shared` page separately checks actual default/custom script transport and missing suppliers. These results do not replace native catalog tests, upstream assertions or hosted verification.


Initial browser startup calls the fixed web activation audit; failed imports, activation and missing-service Pending entries reject and clean up. Transient management disconnects preserve plugins and drafts. The public client accepts `transport.fetch`, `transport.openEvents`, `recovery` and manual `reconnect()`. The fixed connection controller owns handshake deadlines, retry/backoff and offline/online handling over the native HTTP/SSE carrier. Closing the owner rejects new writes, cancels reads and awaits withdrawal. Recovery never replays uncertain mutations.

## Application invocation

```console
cordis run ./profile --resume abc --source app-owned-value
cordis run ./profile --source ./feed --url http://127.0.0.1:5080 --authorization-env CORDIS_TOKEN -- --help
```

The launcher parses its own options until `--` or the first unrecognized token; the remaining arguments are copied verbatim into `CommandLineArguments` under `cmdlineArgs`. The application owns parsing, help and errors. The first command's `--source` belongs to the application. The second selects a package feed before the separator. Without `--url`, Generic Host opens no HTTP listener. An empty feed whitelist can run installed packages; acquisition still requires an explicitly selected source.

Before entries mount, the CLI also provides `IApplicationReady` as `appReady` and `ApplicationExit` as `appExit`. Register readiness subscriptions with a Context effect. Readiness commits after tree and host startup; late subscribers run immediately. The application may request exit during activation (for help) or after readiness. The first request starts the fixed upstream five-second grace, including during startup; the CLI awaits orderly tree disposal and forces process exit with that code if grace expires. Ordinary startup has no five-second deadline. Startup/readiness exceptions return failure. Cordis reports effect cleanup errors without rewriting the requested code. Existing HMR uses the same readiness result. Process signal handling remains the .NET Host's responsibility.

Library hosts can provide these Composition contracts through `ProfileSession.StartAsync(prepare: ...)` and own their exit policy; they do not need the CLI or another runtime. The verification flow compiles an independent CLR application and runs the real CLI for argument boundaries, help/error, readiness and cleanup. Controlled carrier checks, browser execution and native management tests are separate evidence.

Generation and publication are separate stages. The native Roslyn analyzer runs during the author's C# compilation and emits typed bindings and descriptors into the author assembly. `TypertArtifacts.GenerateClient(contribution)` later produces `.mjs` and `.d.mts` content explicitly; the author or host owns writing and delivering it. This differs from the pinned tsdown plugin's build-time emission and validation of opt-in `./typert`, `./client/typert`, and `./remote` publication. The independent package consumers demonstrate native consumption, without closing the complete upstream build/publication chain. See the [native authoring procedure](authoring.md#declare-and-generate-native-remote-contracts).

Roslyn also supplies root nullable reference annotations through `TypertCodec.CreateNullable`, because runtime `JsonTypeInfo` erases those source annotations. The native codec adds a null branch and relocates local schema references while retaining non-null recursive children; Client generation projects the resulting boundary as a nullable type. Complete nested generic nullability/type-graph analysis remains open. The repaired projection passed independent package JIT/AOT and strict TypeScript checks on Windows/Linux at `16440e3e0adaac65abf510038495dc7115f1cc6e`.

The fixed Host unary production path runs from [Connection's RPC handler](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/client/connection/src/rpc-host.ts#L261) through [dispatchRpc](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/api/gateway/src/index.ts#L424), [invokeRpc](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/api/gateway/src/index.ts#L677), and [prepareInvocation](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/api/gateway/src/index.ts#L700) to [invokePrepared](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/api/gateway/src/index.ts#L361). A previously aborted signal does not prevent business invocation, and a successful result remains successful after abort. An invoked method's failure becomes `gateway/cancelled` when its invocation signal is aborted. Definition/provider withdrawal has no separate immediate Host-abort mechanism. The native generation checks are an explicit validity adaptation.

The fixed [stream iterator](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/api/gateway/src/index.ts#L1186) checks abort before each read, races `next()` against abort, then awaits invocation close and iterator return in `finally`. The native stream-read repair preserves cancellation and cleanup ordering while settling the pending `MoveNextAsync` before `DisposeAsync`, because native iterator operations cannot safely overlap. It observes a late read failure and yields the failure only after cleanup. A body or cleanup that never settles can keep disposal pending in both runtimes. The serialized cancellation/read cleanup passed package JIT/AOT checks on Windows/Linux at `16440e3e0adaac65abf510038495dc7115f1cc6e`.

### Architecture judgment and author experience

The fixed [official author skill](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/preset/agent-preset/skills/cordis-plugin-development/SKILL.md) and its [host-plugin guide](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/preset/agent-preset/skills/cordis-plugin-development/references/host-plugin.md) expose ordinary Plugin, Service and Config responsibilities. Cordis.NET should keep those ordinary C# paths. Same-process consumers resolve the live Service directly. Authors opt into Remote when crossing an environment boundary; type extraction, artifact publication and registration should progressively move into the existing toolchain.

Recommended direction: authored C# declarations feed Roslyn extraction, then a serializable compiler-independent model. That model feeds separate projections for native bindings, typed .NET contracts/clients, JSON contracts and optional TypeScript artifacts. Runtime contributions remain owned by existing Loader/Registry mechanisms. This extends the existing Typert implementation rather than replacing Core, Composition, HMR or management APIs.

The fixed [generator model](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/typert/generator/src/model.ts) separates `FaceModel`/`TypeGraph`, invocation metadata and authored-versus-codec types. It includes non-Remote Services, Events and reference objects. Its [emitter](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/typert/generator/src/emitter.ts) consumes that model. Native extraction must preserve the corresponding responsibilities, with explicit C#/CLR adaptations rather than an arbitrary-C# or TypeScript-compiler equivalence promise.

| Information source | Appropriate authority | Limit |
|---|---|---|
| Roslyn symbols and semantic analysis | Authored declarations, selected public members, type relationships, nullability, Remote markers, identities and source diagnostics | Compiler objects remain extraction inputs, never runtime model state |
| Compiler-independent model | Stable declaration relationships and separate serialization/invocation projections | No service instances, CLR `Type`, delegates, `JsonTypeInfo`, Expression Trees or general live-object graph |
| STJ metadata, Schema and explicit codec policy | Actual JSON names, converters, requiredness and supported wire shapes | Cannot reconstruct all authored types, method scope or borrowed/owned Context semantics |
| Runtime descriptor and binding | Invocation admission and native dispatch for an active contribution | Cannot become the complete source model or a persistent contract cache |
| Explicit Reflection adapter | Optional JIT extraction/validation for a selected assembly | Not a mandatory author path, global assembly scan or Native AOT fallback |

Schema/OpenAPI-first organization would simplify some DTO/HTTP generation but lose declaration relationships and lifecycle meaning unless a separate model reintroduced them. Reflection-first organization would leave source facts incomplete and add runtime-loading/AOT constraints. Neither is a suitable sole authority for complete Typert. Quantum and a new object-graph framework are unnecessary for this decision.

Compilation-model caches may contain immutable data keyed by exact build inputs and generator version. Runtime codecs, delegates and metadata have owner/bundle-generation lifetime. Persistent registry history must not retain retired runtime bindings. Caller-generated DTOs or explicitly shared, versioned contract assemblies are preferable to a typed client referencing a collectible provider implementation. One dispatch difference needs its own disposition: pinned Host validates the live Service/binding before concurrent parameter lookups; the candidate performs lookups sequentially before checking the live Service.
